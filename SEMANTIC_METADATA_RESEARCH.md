# Native metadata for a typed material and construction map

Read-only research, 2026-10-14. No exporter, schema, production code, canonical database, or running game changes. The report inspects native declarations and proposes a bounded experiment. It does not claim a measured improvement from a semantic map.

## Decision

Test typed form and operation guidance against the current dump before requiring another game export. Preserve native material, form, construction role, declared amount, source-contribution evidence, and path history as separate dimensions. Do not promote the flat union of additional material constituents.

That flat-union treatment changed hints for 5,397 resources. Fresh Volcanus fell from six paths covering eight of fifteen target branches to one path covering two of fifteen. Both reached 20,000 queued states. Peak queue rose from 6,334 to 18,438. Casing, hull, and double-plate branch coverage was unchanged. These values were checked in the main agent's [constituent-probe.json](exports/search-research-20261014/constituent-probe.json). A lower runtime or fewer examined states is not an improvement when useful coverage is lost.

The missing Hastelloy associations have a concrete native owner. GT++ generated components expose material and form directly. Complex casings and machine components have different role owners, so their construction roles can be captured without assigning a chemical material from their names. A complete composition or atom-origin model remains unsupported for those assemblies.

## Generated GT++ material and form owners

### Direct item fields

`gtPlusPlus.core.item.base.BaseItemComponent` exposes `public final Material componentMaterial` and `public final ComponentTypes componentType`. `ComponentTypes.getGtOrePrefix()` returns the native prefix. `BaseItemGear` binds `ComponentTypes.GEAR`, and `BaseItemPlateDouble` binds `ComponentTypes.PLATEDOUBLE`. Their parent constructor registers the item from its material/type and registers corresponding OreDictionary entries. A native exporter can read those object fields from the existing `ItemStack.getItem()` without parsing item names. [BaseItemComponent at the runtime commit](https://github.com/GTNewHorizons/GT5-Unofficial/blob/0c2037baa0a0c145f4f2e021729cf5621a1850f5/src/main/java/gtPlusPlus/core/item/base/BaseItemComponent.java#L40), [gear subclass](https://github.com/GTNewHorizons/GT5-Unofficial/blob/0c2037baa0a0c145f4f2e021729cf5621a1850f5/src/main/java/gtPlusPlus/core/item/base/gears/BaseItemGear.java#L6), [double-plate subclass](https://github.com/GTNewHorizons/GT5-Unofficial/blob/0c2037baa0a0c145f4f2e021729cf5621a1850f5/src/main/java/gtPlusPlus/core/item/base/plates/BaseItemPlateDouble.java#L6)

These declarations support `gearGt` and `plateDouble` as forms. At the exact tag, `OrePrefixes.gearGt.getMaterialAmount()` is `4 * GTValues.M`, while `plateDouble` is `2 * GTValues.M`. These are native nominal form amounts. They do not establish elemental or molecular quantities for a custom material without a validated quantity profile. [Prefix definitions and amount getter](https://github.com/GTNewHorizons/GT5-Unofficial/blob/0c2037baa0a0c145f4f2e021729cf5621a1850f5/src/main/java/gregtech/api/enums/OrePrefixes.java#L892)

### Material registry and component declarations

GT++ `Material` has public `mMaterialMap`, `mMaterialsByName`, and `mComponentMap`. `getComposites()` returns the declared `MaterialStack` list. `MaterialStack.getStackMaterial()` returns the referenced native material. `mComponentMap` and `registerComponentForMaterial` store native material/prefix to concrete ItemStack associations. The map records one registered stack per material/prefix, so it is not proof of all aliases or variants. Direct component fields cover their own item owner more precisely. [Material registry and component access](https://github.com/GTNewHorizons/GT5-Unofficial/blob/0c2037baa0a0c145f4f2e021729cf5621a1850f5/src/main/java/gtPlusPlus/core/material/Material.java#L46), [MaterialStack](https://github.com/GTNewHorizons/GT5-Unofficial/blob/0c2037baa0a0c145f4f2e021729cf5621a1850f5/src/main/java/gtPlusPlus/core/material/MaterialStack.java#L12)

`MaterialsAlloy.HASTELLOY_W` declares Iron 6, Cobalt 2, Molybdenum 24, Chromium 6, and Nickel 62. `HASTELLOY_N` declares Yttrium 8, Molybdenum 16, Chromium 8, Titanium 8, and Nickel 60. Therefore, an Iron contribution hint exists for the native Hastelloy-W definition. It must not be copied to Hastelloy-N merely because their names share a family. These declarations are native game facts rather than real-world alloy chemistry. [Exact alloy declarations](https://github.com/GTNewHorizons/GT5-Unofficial/blob/0c2037baa0a0c145f4f2e021729cf5621a1850f5/src/main/java/gtPlusPlus/core/material/MaterialsAlloy.java#L296)

For generated blocks, `BlockBaseModular.getMaterialEx()` returns its GT++ material and public `blockType` records the block form. `Block.getBlockFromItem` can identify that native block owner. This does not apply to every metadata casing block. Minecraft block `Material`, including `MaterialCasings.INSTANCE`, is a behavior category and is not a GT++ composition declaration. [Generated block owner](https://github.com/GTNewHorizons/GT5-Unofficial/blob/0c2037baa0a0c145f4f2e021729cf5621a1850f5/src/main/java/gtPlusPlus/core/block/base/BlockBaseModular.java#L30)

### Avoid convenience lookups that manufacture evidence

`Material.getComponentByPrefix` fills missing cache entries and may search GT material names or OreDictionary names. `getGTMaterial()` calls a name-based equivalence routine. `generatesPrefix()` calls that component getter and is explicitly described as unreliable in native source. Those APIs can be useful for native item generation, but they should not be presented as a pure, exact reverse association lookup. Prefer direct fields and already-populated map entries, recording the owner and lookup semantics. [Component lookup](https://github.com/GTNewHorizons/GT5-Unofficial/blob/0c2037baa0a0c145f4f2e021729cf5621a1850f5/src/main/java/gtPlusPlus/core/material/Material.java#L820), [equivalence and generation checks](https://github.com/GTNewHorizons/GT5-Unofficial/blob/0c2037baa0a0c145f4f2e021729cf5621a1850f5/src/main/java/gtPlusPlus/core/material/Material.java#L1569)

## Construction roles have separate native owners

**Volcanus Casing:** `GregtechMetaCasingBlocks3` binds `GregtechItemList.Casing_Adv_BlastFurnace` to metadata 11. More directly, `gregtech.api.casing.Casings.VolcanusCasing` binds `ModBlocks.blockCasings3Misc` and meta 11. `Casings.getBlock()` and `getBlockMeta()` expose that association. `MTEAdvEBF.getStructureDefinition()` accepts the same block/meta as a casing element. This establishes a source-backed construction role and a concrete identity witness, without assigning a primary metal. The block getter initializes a cached block reference, so a future exporter must call it after native registration readiness. [Casing registration](https://github.com/GTNewHorizons/GT5-Unofficial/blob/0c2037baa0a0c145f4f2e021729cf5621a1850f5/src/main/java/gtPlusPlus/xmod/gregtech/common/blocks/GregtechMetaCasingBlocks3.java#L50), [casing owner](https://github.com/GTNewHorizons/GT5-Unofficial/blob/0c2037baa0a0c145f4f2e021729cf5621a1850f5/src/main/java/gregtech/api/casing/Casings.java#L768), [actual structure use](https://github.com/GTNewHorizons/GT5-Unofficial/blob/0c2037baa0a0c145f4f2e021729cf5621a1850f5/src/main/java/gtPlusPlus/xmod/gregtech/common/tileentities/machines/multi/processing/advanced/MTEAdvEBF.java#L140)

**Computer Cube:** `MetaGeneratedItemIDs.Gregtech_Computer_Cube` is ID 55. The native custom-item registration uses the GT++ offset 32000, giving meta 32055. This is outside the generated-material prefix region below 32000. The registration binds `GregtechItemList.Gregtech_Computer_Cube` and supplies electrical stats with tier 5. `GTMetaItem.getElectricStats(ItemStack)` reads the metadata-specific declaration, and `GTMetaItemBase.getTier(ItemStack)` returns its tier. Missing stats produce `Integer.MAX_VALUE`, which must be recorded as unsupported rather than a real tier. Electrical-item tier is separate from a recipe's voltage tier and a machine's runtime capabilities. [Custom ID](https://github.com/GTNewHorizons/GT5-Unofficial/blob/0c2037baa0a0c145f4f2e021729cf5621a1850f5/src/main/java/gtPlusPlus/xmod/gregtech/common/items/MetaGeneratedItemIDs.java#L13), [registration and electrical stats](https://github.com/GTNewHorizons/GT5-Unofficial/blob/0c2037baa0a0c145f4f2e021729cf5621a1850f5/src/main/java/gtPlusPlus/xmod/gregtech/common/items/MetaGeneratedGregtechItems.java#L184), [tier API](https://github.com/GTNewHorizons/GT5-Unofficial/blob/0c2037baa0a0c145f4f2e021729cf5621a1850f5/src/main/java/gtPlusPlus/xmod/gregtech/api/items/GTMetaItemBase.java#L419)

Its registration tooltip says reusable, but that does not establish nonconsumption in every recipe. The captured recipe's consumed/presence slot remains authoritative. Thaumcraft aspects in that registration are also not material-composition quantities.

**Robot Arm IV:** `ItemList.Robot_Arm_IV` is a native component symbol, registered in `MetaGeneratedItem01`. Its symbol establishes the intended component identity and gives a bounded basis for a curated component-role/tier mapping. The current ItemData has no OrePrefix, so Graphene must not become its form or construction role. `ItemList.getInternalStack_unsafe()` exposes the registered stack, which a future exporter must only read or copy. GT++ `GregtechItemList.get()` instead applies unification, so its returned stack is a preferred native anchor rather than proof of every literal alias. [Robot-arm registration](https://github.com/GTNewHorizons/GT5-Unofficial/blob/0c2037baa0a0c145f4f2e021729cf5621a1850f5/src/main/java/gregtech/common/items/MetaGeneratedItem01.java#L2620), [raw stack accessor](https://github.com/GTNewHorizons/GT5-Unofficial/blob/0c2037baa0a0c145f4f2e021729cf5621a1850f5/src/main/java/gregtech/api/enums/ItemList.java#L3565), [GT++ unifying accessor](https://github.com/GTNewHorizons/GT5-Unofficial/blob/0c2037baa0a0c145f4f2e021729cf5621a1850f5/src/main/java/gtPlusPlus/xmod/gregtech/api/enums/GregtechItemList.java#L1064)

**Volcanus Controller:** native registration creates `MTEAdvEBF`, whose `getRecipeMap()` returns `blastFurnaceRecipes`. `MetaTileEntity.getStackForm` associates its machine block and meta-tile ID. A machine-class/recipe-map role is possible from native owners. A multiblock's effective voltage and coil state are runtime facts, so a static recipe-map role is not machine-execution proof. ## Quantity and NBT certainty

GT++ `MaterialStack` is not GregTech's GT-unit `MaterialStack`. Its constructor takes a double described as parts out of 100, rounds to two decimals, and stores split integer/fraction fields. Public `getPartsPerOneHundred()` returns only the integer field when it lies between 1 and 100, otherwise 100. Fractional declaration detail is therefore not recoverable through that getter. Preserve these as native declared relative parts, with the API basis and limitations. Do not call them exact elemental counts, mass fractions, or mole fractions. [GT++ quantity semantics](https://github.com/GTNewHorizons/GT5-Unofficial/blob/0c2037baa0a0c145f4f2e021729cf5621a1850f5/src/main/java/gtPlusPlus/core/material/MaterialStack.java#L17)

`Material.smallestRatio` is a native simplified integer ratio. `RecipeGenBlastSmelter` uses those ratios to construct dust inputs, uses a different 1000-unit convention for nonsolid component fluids, and scales molten output using 144 times the input part count. Actual captured recipe quantities remain the safer transformation witness. A nominal form amount plus a component tree is insufficient for a new universal chemical accounting profile. [Recipe generation evidence](https://github.com/GTNewHorizons/GT5-Unofficial/blob/0c2037baa0a0c145f4f2e021729cf5621a1850f5/src/main/java/gtPlusPlus/xmod/gregtech/loaders/RecipeGenBlastSmelter.java#L119)

Robot Arm IV's existing explicit ItemData composition declares Graphene 24 GT material units, TungstenSteel 9, Tungsten 8.5, and NeodymiumMagnetic 1.5. Its accounting remains unresolved. These are recycling associations, not atom provenance or chemical purity. Association `byproducts` are additional material declarations and must not be confused with recipe-output byproducts.

`GTOreDictUnificator.getItemData` uses an item/metadata map and a wildcard-metadata retry. Its map strategy ignores NBT. The current exporter records that limitation. Direct generated-component fields describe the item owner, not necessarily the semantic effects of arbitrary NBT. Preserve registry, metadata, typed NBT, matching predicates, and the evidence scope. Do not unify resource identities because two records receive the same material/form label. [Native lookup](https://github.com/GTNewHorizons/GT5-Unofficial/blob/0c2037baa0a0c145f4f2e021729cf5621a1850f5/src/main/java/gregtech/api/util/GTOreDictUnificator.java#L493), [NBT-insensitive strategy](https://github.com/GTNewHorizons/GT5-Unofficial/blob/0c2037baa0a0c145f4f2e021729cf5621a1850f5/src/main/java/gregtech/api/objects/GTItemStack.java#L27), [current MaterialFacts policy](exporter/src/main/java/dev/gtnh/data/MaterialFacts.java)

## Bounded next experiment and optional export

The next experiment can use the current snapshot's prefix associations, actual OreDictionary form labels, and recipe contexts. Separate candidate form changes, material transformations, and assembly-role transitions. An operation-family label alone does not determine these classes. Use concrete consumed-slot/output witnesses and the associated native evidence. Keep source-history penalties and target ingredient branches separate from form similarities.

Do not require a complete material catalog to start. Keep unknown cases concrete and searchable. Preserve exact OR predicates, NBT, tier filters, quantities, chance, and required/excluded intermediates. Internal form-conversion witnesses must consume the same global queue/work allowance. Their native microstep costs remain visible even when several equivalent variants share an abstract guidance class. The purpose is to reduce redundant exploration, not to declare every same-material conversion free or lossless.

If this shows a same-budget benefit, a cheap additional native capture can deepen the existing `MaterialFacts` owner with:

- GT++ generated item/block associations from direct material/type fields
- A snapshot-scoped GT++ material catalog containing native identity, component references, declared relative parts, and their quantity basis
- Registered concrete material/form anchors from existing maps, with coverage limited to those anchors
- Casing symbols with exact block/meta associations
- Selected native component symbols and their curated role mappings, with electrical or declared component tier kept separate from recipe voltage

No new material facts for casings or Computer Cube should be synthesized from their construction recipes. Recipe inputs establish dependencies and can support explanatory roles, but recycling, coproducts, and consumption semantics make them an unsafe universal product-composition model. Keep these added hints separate from chemical accounting eligibility. No new dependency is needed, and none was added in this task.

Measure coverage before considering a full map: direct GT++ owners, native prefix availability, OreDictionary-only form evidence, component-tree completeness, supported amount basis, casing/component role witnesses, aliases, tagged identities, and conflicts. Report the intersections and the benchmark endpoints. Five inspected examples are not a pack-wide census. The earlier roughly 24% primary-material coverage does not measure GT++ owner coverage or guarantee comprehensive form/role metadata.

## Evidence and limits

Raw exact-tag source extracts, canonical resource/group observations, the bounded constituent-probe summary, and `source-manifest.json` are in `exports/search-research-20261014/semantic-metadata/`, which is Git-excluded. Native source discovery used codebase-memory, with exact-tag Git reads for verification. Official GitHub confirmed the tag. Read-only MCP calls confirmed the five resource identities and two OreDictionary groups. No game API was invoked, no build or Gradle task was run, and no exporter or schema implementation was attempted.

The report establishes feasible native evidence sources and their limits. It does not establish runtime registry coverage beyond the captured examples, successful class linkage for a new exporter, a complete quantity model, or an improved search. Those claims need their own measured experiment.
